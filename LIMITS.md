# LIMITS — what `dromas-server` limits, why, and where it is weak

Every limit `dromas-server` enforces, what it protects, who pays for it, when it is taken, and what is known not to hold. It is here to be checked: a way around one that § Known weaknesses does not list is reported privately (`SECURITY.md`); a cost one does not bound is an issue.

**These are `dromas-server`'s limits, not the protocol's.** The specification (`PROTOCOL.md` §11.5, in the client repo) says what a client must handle: a `429` with `Retry-After`, a few codes, and the promises every server system keeps. How much, and of what, is each server system's own choice; another server system may limit differently. The reference clients obey whatever a server system answers. **No value is written here:** each limit is a member of the limits file (`serve --limits`, `README.md`), laid over its default, and `dromas-server limits default` prints every default as such a file. A limit's name below is its member.

## The rule

1. **No call with a pass is free, and nothing that reaches a table or a signature check is free.** Memory is cheap and the tables are not, but bandwidth can cost more than either, and a call that is cheap once can take a server system down in volume. So every call a mailbox makes spends from its budgets (a successful poll is limited for the bytes it moves, not for what it reads), and a call with no pass spends from its address's counts when it costs `dromas-server`: a registration, a read that finds no mailbox, a check that fails. **Every request is counted before anything is done for it** (`TestEveryRequestIsCountedBeforeAnythingIsDone`). A call that carries a pass this process has checked, of a mailbox live in its memory, on a route that takes that mailbox's pass, is its mailbox's, and spends the mailbox's budgets: a send takes any mailbox's, a call about a mailbox only its own, and a mailbox revoked, or whose current certificate its revocation of certificates covers, has no call that is its mailbox's: its identity's calls, which are taken, spend its address's budget until it renews. Every other spends one budget of its address, sized for floods alone, at one gate in front of every route, before its route does anything: a call with no pass; the read of a mailbox, which takes none, whatever it carries (the client repo's #352); one with a pass the process has not checked, whose parse and signature checks come after; a registration and a renewal, whose passes are read after their bodies; a revocation, the link page and a site's pages; a request no route matches; and a request of a retired version, which is answered `410 client_version_unsupported` before any route is matched and spends nothing else (`PROTOCOL.md` §11.4 rule 0). Let's Encrypt limits every endpoint per address the same way, in front of its check of a request's signature. Until its pass is checked, a call is its address's. Before that count `dromas-server` reads the request's head, to what the longest call needs, and hashes its `Authorization` value, and nothing more: what it costs is what reading those bytes costs. The budget is set far above what an honest crowd behind one address makes, which must never be refused; a mailbox signs a new pass once in ten minutes.
2. **Who pays is who the call proves itself to be.** A call with a mailbox's pass is the mailbox's. A new message is its recipient's too. A registration, a read that finds no mailbox, a check that fails, a call with no pass and one whose pass `dromas-server` has not checked yet are the caller's IPv4 address's or IPv6 /64's: every IPv6 end site holds at least a /64. An IPv6 zone names an interface of `dromas-server`'s host and is no part of the address: a link-local caller is counted by its /64 too. Each such count is its IPv6 /48's too, the range Let's Encrypt counts new accounts by, so a /48 spends no more of any than its own count however many of its 65,536 /64s it calls from; an IPv4 address has no /48 count. Every limit keyed by an address goes through one type that holds both counts (`addressLimit`) (`TestLookupsArePaidByTheirCaller`, `TestMissesPerIP`, `TestFailedPassesAreCountedPerCaller`, `TestAZonedCallerIsKeyedByItsSlash64`, `TestRegistrationsAreCountedByTheRange`, `TestEveryAddressLimitIsCountedByTheSlash64AndTheSlash48`).
3. **What would change nothing is answered before what costs.** The orders `PROTOCOL.md` fixes, its §11.4's two rules (a retired version first, a mailbox's state before any pass), §11.5's request that would change nothing and §11.2's preconditions, are `dromas-server`'s claims, each beside its test in `SECURITY.md`. `dromas-server` also answers a statement no higher than the one held, a renewal's or a revocation of certificates', before its signature is checked (`TestAStatementOutOfOrderIsRefusedBeforeItsSignature`, `TestAFloorNoHigherIsAnsweredWithoutACheck`). Any other order is a route's handler's.
4. **A count is reserved before the work it guards, and kept or given back after.** One checked first and counted after lets calls in flight at once all pass on one count. Where only the outcome says whether a call counts (a lookup that may find no mailbox, a signature that may fail), the token is taken first and given back if the call turns out not to count; a refusal that only reservations still in flight would cause waits a moment for one to settle. Every reservation is settled however its call ends, a panic included. A write runs to its end however its caller goes, and a count reserved for it is kept when the write was applied or when its outcome is unknown, which leaves open whether it was applied (an answer lost, a statement whose bound ended mid-way, a `COMMIT` with no answer, or any error its backend did not state as a refusal), and given back only for a refusal that was stated: by PostgreSQL, an answer of its own, after which the statement or its transaction rolled back, or a write pgx never sent; or by the store, of a write it did not make (a failed condition, a send whose body's put failed wrote no message, a send that met another's message of the same ciphertext). The store reads a write's outcome in one place (`Memory.write`, `pgOutcome`, `ARCHITECTURE.md` § The store), and each handler settles its counts by it (`mayHaveApplied`). pgx retries nothing it sent, so one attempt is the whole write. A send whose row meets one of the same id hands back that row: one of the write's own time (a message of its `received_at`) is the write, made and counted as made, and another's is a refusal stated. So a caller who hangs up mid-write, or a write PostgreSQL applied whose answer was lost, spends what it would have spent (`TestDailySendsAreTakenBeforeTheWrite`, `TestAReservationWaitsForOthersInFlight`, `TestAPanicSettlesItsReservations`, `TestAWriteOutlivesItsCallersHangUp`, `TestACountIsKeptWhenItsWriteMayHaveBeenApplied`, `TestARefusalAWSStatedGivesTheCountBack`).
5. **A mailbox's counts are spent only by calls that showed its pass or whose signature its identity made, once checked, and by messages to it that passed every check.** A stranger never spends one before a check that could refuse it: a count of the mailbox's that a failed call could spend would be a way to lock its owner out.
6. **What an account may lift is volume:** what a mailbox sends, what it receives, what it takes out, how large, and its calls, with the writes of its own record those calls make (an ACL, an adopt, a leave). Registrations, revocations, lookups and failed checks are not for sale.

## Every limit

**A limit changed by a reload applies to each key's next call** (`TestAReloadedLimitsFileIsInForce`): every bucket keeps, for each key, the time it is full again, and reads it by the new size, as Let's Encrypt's Boulder keeps a key's TAT and reads the limit at each check (`ratelimits/gcra.go`). So a raised limit gives a key that spent its bucket the new rate at once, and the new burst once what it owed at the old rate has passed.

## How a refusal names its limit

Every `429 rate_limited` names its limit in `quota_id`, the name in the last column above, and whom it counted the call against in `subject`, `mailbox` or `ip` (`PROTOCOL.md` §11.5). Where a mailbox's own count in memory refuses a call, `dromas-server` also reads the mailbox's other counts the same call would spend, taking nothing from them, and answers with the longest wait, under that count's name, as RFC 8555 §6.6 asks: a renewal's calls and its renewals or certificates a day, and a registration's two counts. A count behind work (a read of storage, a signature check, the recipient's counts, and a send's sends a day, which only the dedupe shows a send would spend: a retry spends none) is not read ahead of it, so a caller can meet it once the first wait is over; the reason is the client repo's `PRECEDENTS.md`.

## Accounts: where a mailbox's limits are read

`limitsFor` reads a mailbox's account, from a cache, and returns its limits. Today one kind of account lifts anything: an unmetered one, whose mailboxes have no daily send limit, the largest size cap, no budget of calls or of new messages taken out, and new messages received at the ceiling, in buckets of their own (`receivesAt`). A mailbox in no account is known to be so from memory, with nothing read.

**What is planned for paid volume, and not built:** an account carries a value for each volume lever (sends a day, calls, new messages received and taken out, the size cap) and a price; `limitsFor` applies the account's values to its mailbox, as a sender and as a recipient; each refill of a budget has buckets of its own, as the ceiling's has; no account lifts new messages received past the ceiling. Nothing else is to be sold.

## Known weaknesses: read these first

1. **Every budget and count is per process,** in memory, and so are the cursor each mailbox was handed last and the sends in flight, and a restart starts every mailbox afresh (the numbers a day included). Under routing by address (`ARCHITECTURE.md` § Routing by address) a mailbox's own counts, the mailbox cap among them, are its shard's process's alone; one keyed by a sender (its sends a day) or by the caller's IP address is spent on each process it reaches, so up to N times with N shards. Sharing those counts is not built.
2. **The budget of new messages received is shared by every sender, and it is on by default.** Enough senders can spend a mailbox's, and delay everyone else's messages to it; the messages wait in the senders' outboxes and are sent again. Every sender's own counts bound how much each spends. It is kept on, beside the budget of messages taken out that only the mailbox spends, so `dromas-server` leans to refusing a flood at the door. The budget of messages taken out can be set apart, or off; the budget of new messages received can be set apart, never off or past the ceiling. **A mailbox whose address is published can be delayed this way by a determined enough sender: keep the address of a mailbox you rely on private** (the specification's §15.9). A mailbox's ACL with an allow list (the specification's §11.14) lets a published mailbox take messages only from the senders it names: the refusal comes before the budget is spent.
3. **An address is a coarse key.** Honest mailboxes behind one address (a NAT, a cloud's egress) share its registrations and its misses. Their calls with a pass are their own, but for three things that count against the address whatever a call carries: naming a mailbox that does not exist, a check that fails, and a pass the process has not checked yet, which spends the address's flood budget before it is checked, once in a mailbox's ten minutes. A lookup takes no pass (the specification's §11.8), so every mailbox's lookups, of itself or another, are the address's too. An address that has spent its misses has its next new pass refused until one comes back; a pass the process has seen is unaffected.
4. **What is answered from memory to anyone is limited only by the flood budget of its address** (`request_burst`), which is set far above an honest crowd's use and so lets through a great deal before it refuses. So are the checks of passes the process has not seen, at up to two signature checks for each call that budget lets through: a mailbox that signs a new pass for every call has as many checked as its address's budget allows, and each IPv6 /64 has a budget of its own, within its /48's. Each such answer costs `dromas-server` only its bytes, but for the read of a mailbox that exists and is not in the record cache (`--mailbox-cache`), which costs one read of the database; cycling past the cache takes more real addresses than it holds, which nobody can find by guessing. A connection that never completes a request spends nothing. The read of a mailbox is one of these whatever it carries: it takes no pass (the client repo's #352).
5. **A pass is checked once in each process,** at two signature checks; after that it is a lookup in memory.
6. **The one large read can still be held for as long as a body takes at the minimum rate:** for a body of the largest cap, hours. Only a mailbox whose account lifts its cap can take it, and a send waiting for it gives up after `body_timeout`.
7. **Nothing bounds how many sends wait for the large read,** and each holds the free size it has read while it waits.
8. **A count given back after its key's refill caught up returns a token a later call took** (#37): a count is given back as Let's Encrypt's limiter refunds one, one interval off its key's time and never before now, so each reservation held while its key's bucket refilled, then given back, lets one call more through than the bucket held.
9. **The long polls are one pool a process, shared by every caller** (`max_long_polls`): a mailbox holds one, and one IPv4 address or IPv6 /48 at most `max_long_polls_per_range`, so a party fills it with a mailbox for each list, from `max_long_polls` ÷ `max_long_polls_per_range` ranges. A /48 is free from some tunnel brokers, and only the registration budgets bound the mailboxes. Once the pool is full, a long poll of a mailbox that holds none is answered `503` and its client polls at the poll interval: long polls degrade, and no message is lost.

## The operator: clearing an address, and who spends a limit most

`dromas-server limits clear --socket PATH --ip ADDR` forgets what the limits keyed by an address hold of one caller, as if it had never been seen: its misses, its registrations, its sends before their pass and its calls with no checked pass. An IPv6 address, with or without a zone, is cleared by its /64 and by its /48, as it is counted. It answers `{"address": <the key cleared>, "cleared": [<the names of the limits that held anything>]}`. A mailbox's own budgets are not touched.

`dromas-server limits top --socket PATH --limit NAME [--count N]` lists the keys one limit holds deepest in debt now, deepest first: which mailbox takes the most new messages (`mailbox_rate_limited`), which address registers the most (`registrations`). A limit is named as a refusal names it: a `rate_limited`'s quota, or the code of its own (`mailbox_rate_limited`, `fetch_rate_limited`); `fetch_rate_limited` names both the first fetches' limit and the repeat fetches'. It answers `{"limit": NAME, "keys": [{"key": <a mailbox's address or a caller's>, "full_in": <seconds until its bucket is full>}]}`, reads memory and keeps nothing. How often each limit refuses is the metrics' (`ARCHITECTURE.md` § Metrics); which key it refuses is no metric, since an address or a mailbox is no label.

Both go through the running `dromas-server`'s `--admin-socket`, because the counts are in that process's memory and a process of its own could not reach them; so each sees one process's (weakness 1). The socket is a Unix socket `dromas-server` makes 0600 from its bind on, never on the API's listener; put it in a directory no other user can write, since one who can may replace it. `dromas-server` logs that a command ran and which limits it touched, never an address or a mailbox.

## Tested

Each limit and each refusal's name is held by the tests in `internal/server/` and `cmd/dromas-server/`, whose names say which; a rule above names the tests that hold it. They run on the in-memory backend, and on PostgreSQL with `DROMAS_TEST_POSTGRES` set (`AGENTS.md`), under the same memory.
