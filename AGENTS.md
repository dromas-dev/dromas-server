# AGENTS.md — dromas-server

`dromasd`: the server of Dromas (dromas.dev), end-to-end encrypted, sender-verified mail between bots. **This repo is PUBLIC (Apache-2.0): every push publishes.**

**Judging whether Dromas is secure → `SECURITY.md`** (what this server must still get right, the code and tests that hold each, and how to report a vulnerability privately), **and the client repo's, which holds what protects a message. Changing it → § Contributing, § Invariants and § How a design is chosen.**

## Contributing

### Sign off every commit

**Every commit carries your human's sign-off, made with `git commit -s`** (the Developer Certificate of Origin: `CONTRIBUTING.md`).
- **It is their certification, not yours.** Tell them the repo requires it. With their say-so you may run `git commit -s` for them: it writes the line from their git identity.
- 🛑 **Never sign as yourself, never write a `Signed-off-by:` line by hand, and never put anyone else's name on one.**
- **Name yourself** in an `Assisted-by:` or `Co-Authored-By:` trailer.
- A pull request whose commits lack the line fails the DCO check and is not merged. `CONTRIBUTING.md` has the commands that add it to commits already made.

### What goes here, and what never does

- **Here:** the server's code, its tests and its design docs (`README.md` has the table).
- 🛑 **Never here:** a secret; a hostname, address, account id or resource name of any deployment; what a deployment costs or how its limits are set; anyone's private words. A deployment's notes belong to its operator.
- 🛑 **No client code here, and the client imports nothing from here.** This repo imports the client's `protocol/` and `sshsig/`.
- **The specification is `PROTOCOL.md` in the client repo**, and every `PROTOCOL.md §N` here means that file. A change to the wire, a check or a refusal is made THERE, in the same client commit as the code. How this server does it goes in `ARCHITECTURE.md`, and its limits in `LIMITS.md`.
- 🛑 **A setting's VALUE goes in no doc:** name the flag (`dromasd serve -h` reads it). A new limit, or a change to what one bounds or when it is taken, gets its row in `LIMITS.md` in the same commit.
- **`SECURITY.md` is the one place for how to report a vulnerability and for each of the server's security claims beside what holds it;** a change to one edits its row in the same commit. The threat model is the client repo's `PROTOCOL.md` §15, Security considerations.
- **No comparison tables here.** The one comparison doc is `PRECEDENTS.md` in the client repo, and this server's own build choices are its Part 3: point there.
- **No judgement is written as a fact,** on any page, in a comment or in an issue: write what was measured, read at a source or decided. Nothing ranks one cipher, key type or design over another without the source that says so.
- **The server's own page outside `/v1/` is `/to/<address>`,** the page a box's link opens (`internal/server/link.go`). **With `-site-backend` every request outside `/v1/` and `/to/` is passed to a deployment's own web server, as a reverse proxy passes it, and its answer back as it came, a 404 among them** (`internal/server/site.go`); under `/v1/` and `/to/` every answer is the server's. 🛑 No site's content or logic goes in this repo.

### Before every push

- `scripts/check.sh push`: gofmt, vet, every test with the skip check and `test/interop.sh` (`full`, what CI's test job runs), then `golangci-lint run ./...` (`.golangci.yml`, the client repo's file: change both together) and govulncheck at the version the script pins. While working, `scripts/check.sh` alone: vet and the tests `-short` keeps. **CI runs `scripts/check.sh full` on every push to `main`, every pull request and every merge group, against the dromas-client release `go.mod` requires** (`.github/workflows/ci.yml`), where a test that skips fails the job, but the AWS tests and the cost measurement.
- **Tests run in parallel** (`t.Parallel()`); a test of 5 s or more skips under `-short`, saying so, and CI never passes `-short`. The tests build with `-tags dromas_nofsync`, so the client they drive flushes nothing to the disk (the client repo's `client/fsync.go`).
- **Dependencies move as dromas-client's `AGENTS.md` says:** Dependabot's weekly pull requests (`.github/dependabot.yml`: the modules, the actions and the `Dockerfile`'s images), each merged once CI passes. `go.mod` requires a client release; the server pull request that needs a new one takes it with `go get github.com/dromas-dev/dromas-client@<version>` and `go mod tidy`, and Dependabot moves every other module. **To work on both at once, a `go.work` beside the two checkouts (`go work init ./dromas-server ./dromas-client`; untracked, never committed) builds this repo against the client's checkout;** dromas-client's CI runs `scripts/check.sh full` here that way, against its own commit, so a client change that breaks the server fails there first.
- After a change to a handler or a store: `test/interop.sh`, and the tests on AWS. They run on the in-memory store unless `DROMAS_TEST_MSGS_TABLE` is set (`onAWS`), which runs every test on DynamoDB and S3 Express plus the AWS-only ones, on the tables and the bucket `DROMAS_TEST_BOXES_TABLE`, `DROMAS_TEST_MSGS_TABLE`, `DROMAS_TEST_ACCOUNTS_TABLE` and `DROMAS_TEST_BUCKET` name, all four (`awsTestNames`; one missing fails the tests, naming it) (the crash between each pair of writes, two processes, restart). 🛑 Name tables and a bucket kept for tests, never a running server's.
- A test of client behaviour belongs in the client repo, where the forging-server tests are. This repo tests what the real server enforces.
- 🛑 **A claim about every member of a set is held by a test that builds the set from the code, never by a list typed by hand:** a typed list holds the members its writer thought of, and the next one passes untried. `TestEveryRequestIsCountedBeforeAnythingIsDone` reads its routes from `routes()`, and `TestEveryStoreCallSendsAWSWhatItSentBefore` holds every store call's requests to its file; the client repo's `AGENTS.md` § Tests has its own.
- 🛑 **A protocol token compared in any case is lowered by the client repo's `protocol.LowerASCII`, and by nothing else:** Unicode's case mappings read characters that are no token's as ASCII letters (U+017F as `s`, the Kelvin sign as `k`), so `forbidigo` in `.golangci.yml` refuses `EqualFold`, `ToLower`, `ToUpper` and `ToTitle` of `strings` and `bytes`.
- **Every test server is wrapped in the client repo's `api/apitest`,** which holds each answer to its `api/openapi.yaml` in strict mode, and `routes()` is held to that file's operations (`TestTheRoutesAreTheDescriptions`). A new route, member, status or header goes into that file, in the client repo, first: a test server made without the wrapper checks nothing. A site's pages (passed through by `-site-backend`) are a deployment's and are not described there; the link page is.

### After a push: `needs-audit`

A change that needs a second reader, never by default, gets a new issue labelled `needs-audit` in the client repo, whichever repo changed: one to what the server or a client checks, signs, keys, times or deletes, that its tests and their controls do not show right by themselves, and that nobody else read as it shipped (or what was written after its review has not been read). A change its tests hold, one to the client repo's shell client alone, and one to docs, wording or tests get none. The issue the change fixes closes as usual.
- 🛑 **The issue is the auditor's whole brief:** the commits, the claims to try to break, where to look first, what is already known and open, how to run it, and what closes it. An outside agent with no other context must be able to work from it.
- **Nothing waits on one:** it is not a gate.
- **Whoever audits closes it,** saying what was read, run and tried, and files what it found as one issue in the client repo, `findings: the audit of #N`, as the client repo's `AGENTS.md` says: each finding a numbered item; one of Medium or above, or one that breaks a `SECURITY.md` claim or the wire, also an issue of its own, here when it is this repo's code. The client repo's #45 is the pattern of a brief.

### The maintainers' own commits

`main` takes changes only through a pull request and the merge queue, which tests it on `main` with the pull requests queued ahead of it and squash-merges it once every CI job and the DCO check pass there (`gh pr merge <n>` queues one, or, while its own checks run, has it join once they pass); nobody bypasses that, an org admin included (the repo's rulesets: `gh api repos/dromas-dev/dromas-server/rules/branches/main`). 🛑 A CI job renamed, added or removed is a required check changed in the ruleset in the same change, or every pull request waits on a check that never reports. The maintainer's commits are written with Custos, his AI assistant: they carry his sign-off, by his standing word to it, and name Custos in `Co-Authored-By:`. 🛑 That is his arrangement with his own assistant. A contributor's commits are theirs, with their own sign-off (above).

## Invariants — they hold from the first line of code

- 🛑 **The server never holds a box's private key and never sees plaintext.** A server feature that needs either is wrong. (The echo box is a separate CLIENT process with its own keys.)
- 🛑 **No anonymous sends:** every message is authenticated as a REGISTERED address.
- **The address is the SHA-256 of the identity alone. The identity certifies a WORKING KEY, and signs nothing else but a revocation; mail is encrypted to an age PREKEY the working key signs.** Every renewal is a new key: the server refuses one equal to the box's current key or to one of the newest retired ones still live (`PROTOCOL.md` §11.9), and a client makes each one anew.
- 🛑 **The server holds no signature on a message, and issues no credential.** A message's signature is inside the ciphertext, and a box proves itself with a pass it signs (`PROTOCOL.md` §9.2, §8). A server feature that needs a sender's signature over a message, or a secret the server hands a box, is wrong.
- **Well-defined, RECOMMENDED crypto only:** native age to encrypt, a SEPARATE Ed25519 key to sign. No home-rolled constructions, and no key used for both. An identity may be of another key type the protocol defines (`PROTOCOL.md` §4.1: today P-256, optional); the working key that signs what a box says is Ed25519.
- 🛑 **A new pass is checked in three steps, in this order** (`checkPass`; `ARCHITECTURE.md` § The pass check): the certificate it carries against the hash of the box's current one, the working key's signature, then the identity's signature on the certificate with every rule of a certificate. The first two refuse a pass that is not the box's for one signature check at most. The third is a second check of what a registration checked, and it stays: do not drop it to save its cost, and do not move it ahead of the other two.
- 🛑 **Every request is counted before anything is done for it** (`LIMITS.md`, rule 1): every handler is put on its router by `mount`, through the gate (`gate` in `internal/server/server.go`), where a call is its box's only with a pass this process has checked, of a box live in its memory, on a route that takes that box's pass; every other spends its address's flood budget, and a request no route answers is counted by `unrouted`. Before that count the server reads the request's head, to `-max-header-bytes` in `-header-timeout`, and hashes its `Authorization` value, and nothing more. A new route goes in `routes()`, with whose pass it takes (`passRule`), and `TestEveryRequestIsCountedBeforeAnythingIsDone` holds it to the rule in every state of a box.
- 🛑 **Keyed hashing is HMAC or HKDF only, never `hash(secret ‖ …)`.** A secret the server only recognises, an adopt key, is kept as its plain SHA-256, which is no keyed hash: the server takes the key itself, never its hash. No secret is kept for the server, in a file or anywhere else: memory's one key is made at random by each process and dies with it.
- 🛑 **INDUSTRY-standard API shapes, never something clever.** Go; every API path under `/v1/`; JSON in and out, but a message's ciphertext, which is the body itself, raw, on a send and on a fetch; every byte field in JSON is standard base64 of the exact file bytes, in its one encoding, and every JSON text is read by one set of rules, I-JSON among them, by every reader (`PROTOCOL.md` §11.10, §3.3).
- 🛑 **An empty poll never leaves the process:** no DynamoDB, S3 or Redis round trip. Polls × mailboxes is THE load. The rule is for the steady state; the ONE read that loads a box into a process's memory on its first use is fine.
- **Bodies are served through this server's endpoint, never by a redirect to S3.**
- **Bot-first.** Every error carries a machine code, and most a `hint`, what to do about it, naming the client command that fixes it where there is one, never a raw command line the server could alter; an error given no hint (`fail` with an empty one) carries none.
- 🛑 **Every value in an error's `detail` is also a member of its own** (AEP-193; `PROTOCOL.md` §11.3): `fail` takes a detail's values only as `value`s, each of which sets its member, and `failErr` only a protocol error's fixed words. A client needs nothing from `detail`, `hint` or `title`, and shows none of them. A new code is added in the client repo before this server sends it: its status and its title in `protocol/errors.go`, the Go client's sentence for it in `client/errors.go` (`APIError.words`), and its status in the script's `DR_CODES`.
- 🛑 **The store is designed for provisioned DynamoDB capacity, never on-demand:** any burst read must fit it, which is why memory loads per box on first use and never by a full Scan (`ARCHITECTURE.md` § Startup).
- 🛑 **Clocks: every check is exact at this server's own clock, and a client leaves an hour of room in what it makes** (`PROTOCOL.md` §3.4; the comparisons are `PRECEDENTS.md` § Clocks, in the client repo). Add no allowance to a check. Exactness to the second is for what is cryptographic, not for how long a server holds mail. What the server takes is the room: a pass up to an hour ahead, a prekey up to an hour past the 33 days a client asks for. It takes a certificate only once that has begun by the clock of every box it takes, 10 minutes back (`checkPrekey`), so every reader of what it signs is past its start. Every answer is dated by that clock (`Server.dated`): that is how a refusal for a time states what it reads. 🛑 **A test of anything timed gives the box a clock of its own** (`internal/server/clock_test.go`): every test once shared one clock with the server, and none could see that a box two seconds fast could not register.

## How a design is chosen

- 🔑 **The design priorities, in this order:** 1. the correct encryption · 2. a server that is feasible and fast, not as cheap as possible · 3. simple things simple to the user. Never offer a weaker design to save the server CPU, storage or a round trip: state the measured cost beside the correct design.
- **A speed call is made among standard tools and norms:** never replace a standard function with hand-written code to save CPU, and leave deeper optimisation until real load can be measured.
- 🛑 **The protocol is designed against a server that may be hostile and a network that TLS to that server protects.** Never against whatever proxy or CDN stands in front: it may be named as what it is, never given as a reason for a design.
- 🛑 **A design follows industry practice, read at its source,** never this project's own earlier choice, and a statement of the design that differs from that practice is challenged, whoever made it. A deviation is discussed and justified as part of the design, with its reason in `PRECEDENTS.md` in the client repo. **Where Let's Encrypt meets the same concern as a free public API anyone may call (its limits, renewal, revocation, abuse), its practice is the precedent.**
- 🛑 **A format takes a layout others already use, and its overhead is a fixed number of bytes, never a share of the message.** Read what the standards do, and what went wrong with them, before choosing a layout, and give each option's cost beside it. Every format that cannot change after the freeze gets that look once (the client repo's #39).
- 🔑 **Pre-stable: nothing is final until v1 is declared stable.** Until then, always the CORRECT design, with no weight on backwards compatibility or on leaving the wire alone.
- 🛑 **A rule, format or behaviour of our own is no constraint before the freeze either,** this server's, the spec's or a client's: when one forces a workaround on either side, that is a design question, put to the maintainer with the best design for every side and its cost, and every side changes together (the client repo's #126 audits for it).
- 🛑 **Design for a current client;** an old tool version is never a constraint.
- 🛑 **No invented requirements.** Every limit, margin and constraint traces to a stated need or a measurement.
- **`[proposed]` in `PROTOCOL.md` is not decided.** Build only what is decided.
